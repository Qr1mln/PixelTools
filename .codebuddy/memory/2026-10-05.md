## PixelTools 项目
- 新建 Python 项目 (pixeltools, py>=3.12, uv 管理)。
- 用户需求：模拟"大漠插件"(DM Plugin) 最新版 (3.x) API，重点为「图色模块」与「鼠标键盘模块」。
- 最终确定结构：`api` 包 = **扁平 mixin 版**（用户明确说"没这 window/screen 模块"，否决了面向对象版的 Window/Screen 类）。
  - `api/base.py`(BaseModule 基础/绑定)、`api/image_color.py`(ImageColorModule 图色)、`api/mouse.py`(MouseModule 鼠标)、`api/keyboard.py`(KeyboardModule 键盘)、`api/input_control.py`(InputControlModule 输入锁)
  - `api/__init__.py`: `PtPlugin(BaseModule, ImageColorModule, MouseModule, KeyboardModule, InputControlModule)` 多继承聚合，扁平调用风格 `dm.find_pic()` / `dm.move_to()` / `dm.key_press()`。
  - **方法命名约定 (重要, 用户拍板)**：snake_case 面向对象风格（find_pic / move_to / bind / key_press…），与 Python 惯例一致。注意：用户虽要"模拟大漠 API"且最初用大漠 PascalCase，但明确说"按面向对象来"，并否决了 Window/Screen 类；最终 = 扁平 mixin 模块 + snake_case 方法名。**类名仍是 PascalCase**（BaseModule/PtPlugin 等），仅方法名 snake_case。
  - 返回值约定对齐大漠：int 1/0 成功/失败，str "x|y" 坐标，未找到返回 ""。
  - 各方法为桩 (`...`) + 中文注释，无具体实现 (共 113 个公共方法, 含 bind)。
- **已实现的真实方法** (非桩)：
  - `api/base.py` `bind(hwnd, display, mouse, keypad, mode) -> bool`：用 `pywin32`(win32gui) 校验 hwnd (`IsWindow`) + 记录客户区原点/尺寸；`display/mouse/keypad/mode` 暂存未实现。`bind_window`(大漠 BindWindow) 委托给 `bind` 返回 1/0。
  - `api/mouse.py` `move_rel(dx, dy) -> int`：用 `pywin32`(win32api) `GetCursorPos`+`SetCursorPos` 做相对移动，异常返回 0。注：`move_r` 已由用户/之前改名为 `move_rel`（同语义，更可读）。
  - 这两个文件都用惰性 `import win32gui/win32api`（包内其他桩不依赖）。
- **测试守护价值**：`test_api_surface` 逐一比对 EXPECTED_* 与 `PtPlugin` 实际方法，能抓出"方法被误删/改名"——本次发现 `api/base.py` 的 `bind_window_ex`/`set_sim_mode` 桩被漏掉，已补回。
- 用户偏好（重要）：不要 window/screen 这种人造模块名；采用扁平 mixin 模块划分（基础/图色/鼠标/键盘/输入锁）。

- **DPI 缩放比务必幂等 (最终方案, 覆盖上面那条的说法)**：真正的坑是 **mss 首次构造 `mss.MSS()` 时会把进程切成 DPI-aware**。实测本机(4K@150%)：进程启动未建 mss 时 `GetSystemMetrics(0)=2560`、`GetDpiForSystem()=96`；一旦建了 mss 就变成 `SM0=3840`、`dpi=144`。因此任何基于「mss 宽 / GetSystemMetrics 宽」或首次读取的实现都会**顺序相关**：首调用得 1.5、之后变 1.0，导致截图区域变小、粉色标记错位(用户报"截图的位置不对")。最终 `_dpi_scale()` = **先幂等调用 `shcore.SetProcessDpiAwareness(2)`(失败/已设置均忽略, 回退 `SetProcessDPIAware`), 再返回 `GetDpiForSystem()/96`**，保证与调用顺序无关。验证: 直接调用与 `_grab_region` 内部均为 1.5; 逻辑区 (0,0,1920,1080)→截图 2881×1621; 全逻辑屏 2560×1440→3839×2159; 端到端 逻辑(1000,600)→设备(1500,900) 取色后全屏找色回到 ~(1000,600)。
- **find_color 高 DPI 修复 (重要坑，结论见下条修正)**：`mss` 按**设备像素**截图，而用户传入的 `(0,0,1920,1080)` 是**逻辑像素**。系统开缩放(如 150%)时，整屏找色会只扫到左上角一部分→"找不到"且返回坐标与预期不符。已在 `api/color.py` 的 `_find_color_points` 中按系统 DPI 缩放 (`_dpi_scale()` 调 `ctypes.windll.user32.GetDpiForSystem()/96`，取不到回退 1.0) 把逻辑区域映射为设备像素、裁剪到主显示器 (`sct.monitors[1]`)、扫描后再把命中点 `round((gx1+px)/scale)-ox` 还原为输入(逻辑)坐标系；并对逻辑坐标**去重**(高 DPI 下多个设备像素映射到同逻辑坐标)。`_get_pixel_rgb`(多点找色偏移校验)同样按 scale 换算。注意：测试机疑似 150% 缩放(scale≈1.5)，`test_find_color_ex_all_pixels_when_sim_zero` 曾因设备像素映射回逻辑坐标产生重复点而失败，去重后恢复 33 全绿。`sim=1`+`-000000` 为逐字节精确匹配，差 1 即漏，属大漠预期行为(非 bug)。
- **新增 find_color_preview (找色可视化调试)**：在区域截图上把命中点用粉色 `(255,0,255)` 填充标记并保存图片(可选 `show=True` 调系统查看器，`Image.show()` 已 try/except 忽略无图形环境)。依赖现成包 **Pillow** (`uv add pillow` → `pillow==12.3.0`，pyproject 已声明)，配合 mss 截图，未手写图色基础代码。签名 `find_color_preview(x1,y1,x2,y2,color,sim,dir_=0,out_path="find_color_preview.png",marker=9,show=True) -> (points, path)`。同时把 DPI/裁剪/截图逻辑抽成私有 `_grab_region(x1,y1,x2,y2) -> (shot, gx1, gy1, scale, ox, oy) | None`，`_find_color_points` 已改为复用它(消除重复)；坐标还原公式 `输入(逻辑) = round((gx1+px)/scale) - ox`，反向 `截图内像素 = round((lx+ox)*scale) - gx1`。注意：新增公共方法要同步登记到 `tests/test_pt_api.py` 的 `EXPECTED_COLOR`，否则 `test_total_method_count`(由契约集合求和) 会因 114!=113 失败。测试新增 `test_find_color_preview_marks_and_saves`(断言命中点被填成粉色+文件落盘)，现 34 项全绿。
- **对齐大漠 FindColor 文档 (zimaoxy.com/docs/qscript/dm.findcolor/)**：`api/color.py` 的找色严格按 DM 语义。关键结论：(1) `_color_scan_order` 的 dir 0~8 方向表——约定"描述中第一个方向是快轴(内层)、第二个是慢轴(外层)"，所以 dir 0 "左→右,上→下" = x 内层、行序 `for y in ys for x in xs`；dir 5~8 才是列序/反序。最初实现把内外层写反了(0/1/2/3 实为 5/7/6/8 顺序)，已修正并 33 测试全绿。(2) 颜色串支持大漠格式 `"RRGGBB-DRDGDB"`(各通道十六进制偏差) 与多色 `"|"` 分隔，解析在静态方法 `_parse_dm_colors(color, sim)`；未带 `-偏差` 时回退 `int((1-sim)*255)` 容差；反色 `@`(DM 付费) 跳过。(3) `find_color_e` 现返回大漠风格 `"x|y"` 字符串，失败返回 ""。注意：DM 文档只详述了 FindColor，FindColorEx/FindColorBlock/FindMultiColor 需另查各自子页。
